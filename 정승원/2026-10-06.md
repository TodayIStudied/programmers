## 구간 잘 나누기

### 문제 설명

- 문제명: 구간 잘 나누기
- 문제 URL: [구간 잘 나누기](https://www.codetree.ai/trails/complete/curated-cards/challenge-divide-sections-well)
- 풀이 URL: [내 풀이 코드](https://github.com/HappyPotatohappy/CodingTest/blob/0fea535a86ae355f95b5e087516d20706edf60d0/trail2/구간%20잘%20나누기/divide-sections-well.py)
- 사용 언어: Python
- 분류: Trail 2 / 완전탐색 III / 기준을 새로 설정하여 완전탐색 (난이도: 어려움)
- 길이 n인 수열을 순서를 유지한 채 m개의 연속된 구간으로 나눈다.
- 각 구간의 합 중 최댓값이 가장 작아지도록 나누고, 그때의 최댓값을 출력한다.

### 접근 방식 : 1. 구간 합의 최댓값을 기준으로 정하고 이분 탐색 (결정 문제로 변환)

- 왜 이 방식으로 풀었나?
  - 나누는 방법을 직접 탐색하면 n - 1개의 경계 중 m - 1개를 고르는 C(n - 1, m - 1)가지 경우를 모두 확인해야 한다.
  - 대신 "모든 구간 합을 X 이하로 만들면서 m개 이하로 나눌 수 있는가?"라는 기준을 먼저 정하면, 판정은 앞에서부터 그리디로 O(n)에 끝난다.
  - X로 나눌 수 있다면 X보다 큰 값으로도 항상 나눌 수 있다(단조성). 따라서 가능한 X 중 최솟값을 이분 탐색으로 찾는다.
  - 핵심은 **"최댓값의 최솟값"을 구하는 최적화 문제를 예/아니오 결정 문제로 바꾸는 것**이다.

- 탐색 범위를 정하는 방법
  - `left = max(a)`: 가장 큰 원소는 어느 구간에든 들어가므로 정답은 이보다 작을 수 없다.
  - `right = sum(a)`: 전체를 한 구간으로 두면 구간 수가 1이므로 항상 조건을 만족한다.
  - 하한을 `max(a)`로 잡았기 때문에 판정 과정에서 원소 하나만으로 기준을 넘는 경우가 생기지 않는다.

- 기준 `mid`로 나눌 수 있는지 판정하는 방법
  - `groups = 1`, `current_sum = 0`에서 시작해 원소를 앞에서부터 현재 구간에 넣는다.
  - `current_sum + x > mid`이면 현재 구간을 닫고 `x`로 새 구간을 시작한다. (`groups += 1`, `current_sum = x`)
  - 각 구간을 기준까지 최대한 채우므로, 이 그리디가 만든 구간 수가 기준 `mid`에서 필요한 최소 구간 수다.
  - `groups <= m`이면 가능하다. 구간 수가 m보다 적더라도 구간을 더 쪼개면 최댓값은 늘어나지 않으므로 정확히 m개로 맞출 수 있다.

- 이분 탐색 갱신
  - 가능하면 `right = mid`로 줄인다. `mid` 자체도 정답 후보이므로 버리지 않는다.
  - 불가능하면 `left = mid + 1`로 올린다.
  - `while left < right`가 끝나면 `left == right`이고, 이 값이 조건을 만족하는 가장 작은 기준이다.

- 구현에서 주의할 점
  - 가능할 때 `right = mid - 1`로 줄이면 정답을 건너뛸 수 있다. `left < right`, `right = mid`, `left = mid + 1` 조합을 일관되게 사용한다.
  - 마지막 구간은 `groups = 1`로 시작할 때 이미 세었으므로 반복문이 끝난 뒤 따로 더하지 않는다.
  - "넣을 수 있을 때까지 넣는" 그리디 판정은 원소가 모두 0 이상이라는 전제에서 성립한다.

- 시간복잡도, 공간복잡도 관점에서의 성능 비교
  - 시간복잡도: **O(n log S)** (S = `sum(a) - max(a)`, 탐색 범위의 크기)
    - 이분 탐색을 O(log S)번 반복하고, 매번 판정에 O(n)이 든다.
  - 공간복잡도: **O(n)**
    - 입력 배열을 저장하는 데 O(n)이 필요하고, 판정은 변수 두 개만 쓰므로 추가 공간은 O(1)이다.
  - 다른 방법과 비교
    - 커리큘럼 의도대로 기준 X를 `max(a)`부터 1씩 늘리며 같은 판정을 돌리고, 처음으로 가능한 X를 출력해도 정답이다. 이 경우 시간복잡도는 **O(n · S)**다.
    - 값의 범위가 작으면 선형 완전탐색도 통과하지만, S가 커질수록 이분 탐색이 크게 유리하다.
    - 경계를 직접 고르는 완전탐색은 C(n - 1, m - 1)개의 경우마다 O(n)이 들어 세 방식 중 가장 느리다.
    - 공간복잡도는 세 방식 모두 O(n)으로 같다.

### 회고

- 몇 번만에 성공했는지: 5번
- 잘한 점:
  - "최댓값의 최솟값" 문제를 결정 문제로 바꿔 이분 탐색(파라메트릭 서치)으로 풀었다.
  - 탐색 하한을 `max(a)`로 잡아 판정 로직에서 별도의 예외 처리를 없앴다.
  - `right = mid` / `left = mid + 1` 패턴으로 경계 처리를 일관되게 했다.
  - 각 분기의 의도를 주석으로 남겨 코드만 봐도 판정 기준이 드러난다.
  - 사실 처음에는 전체 가능한 모든 경우를 구하고 그것의 가지를 줄이는 방식으로 구현 했으나 시간 초과로 4번 제출 했다.
- 개선할 점 (AI):
  - 판정 부분을 `can_split(limit)` 같은 함수로 분리하면 탐색 로직과 판정 로직이 나뉘어 읽기와 테스트가 쉬워진다.
  - 판정 중 `groups > m`이 되는 순간 바로 실패를 반환하면 불필요한 순회를 줄일 수 있다. 최악의 시간복잡도는 같다.
  - 같은 판정 함수로 기준값을 1씩 늘리는 선형 완전탐색 버전도 작성해 두면, 커리큘럼 의도와 이분 탐색의 차이를 직접 비교할 수 있다.
